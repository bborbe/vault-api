# Changelog

All notable changes to this project will be documented in this file.

## Unreleased

- feat: Add an `assignee` label to `vault_api_open_tasks`, so an owned record is distinguishable from an abandoned one at the same phase. The gauge carried stage, task_type, phase, job_state and pr_state but not who owns the task, so two records in identical states were indistinguishable and the unowned one — the one that needs a human — could not be picked out. An absent or empty `assignee` is reported as the sentinel `unassigned` rather than as an empty label value, mirroring `job_state`'s `none`: PromQL has no positive matcher for label absence, so only a value is queryable. The value is otherwise carried raw — the assignee population is operator-authored and bounded, and coercing an unexpected value would hide it — and the metric's Help string names the new label. ⚠️ **Every series changes identity: the same record now exports one more label.** A query selecting on the old label set still matches, since labels are additive, but a panel that groups or joins by the full set sees new keys.

## v0.19.0

- feat: **Serve a per-pull-request claim, so two reviews of one repository can run at once instead of queueing behind each other.** The repository claim serialises every review of a repository: `pr-reviewer` takes the repo key, and a second PR's review waits behind the first for as long as it renews — a review that is slow for a legitimate reason blocks every sibling PR in that repository. The new routes are `/api/v1/repos/{owner}/{repo}/pulls/{number}/claim` plus `/renew`, `DELETE` and `GET`, returning `scope: "pr"` and `id: "owner/repo/<number>"`. The executor already derives this key (`DeriveClaimKeysWithBody`) and holds it **alongside** the repository claim, recovering the pair by task id; until now vault-api had no typed route for it, so a caller could list a `pr` claim that no route could act on. ⚠️ **The derivation reproduces the executor's exactly, including two details that look like accidents and are not:** owner and repo are lowercased but the number is **not** (the executor lowercases only the first two, and the number comes from the PR body validated as-is — lowercasing it here would accept an input the executor rejects and split the key space), and the number is validated as a **claim component**, not parsed as an integer (the executor runs `validateClaimComponent` over it, so a stricter integer check would refuse a key the executor can write). ⚠️ **A latent defect was fixed on the way, and it would have failed silently.** The transport requires a `task_id` on every ref write, and `claimTransportTaskID` decided it with `scope != "repo"`. Adding a third scope would therefore have sent the claim's own address, `owner/repo/7`, to git-rest as a task id. Nothing would have errored: the claim would be written with a task id that is not a task, and the executor's recovery pairs a repository claim with its per-PR claim **by task id**, so the pair would have read as two unrelated singles — each then adopted, fenced or released on its own. The test that pins this asserts the transport receives the caller's task id and specifically not `owner/repo/7`.

## v0.18.0

- feat: **Serve `GET /api/v1/claims`, so a caller can ask which claims exist instead of having to know every key in advance.** Until now the claim surface was readable only one object at a time — `GET /api/v1/tasks/{id}/claim` and `GET /api/v1/repos/{owner}/{repo}/claim` — which cannot answer the question a restarting executor actually asks: *which claims do I already hold?* Without that answer the executor cannot see the refs it left behind, so it waits out every lease instead of re-adopting or fencing its own work. The route lists the whole `claims/` namespace in one call and returns, per claim, `scope`, `id`, `holder`, `task_id`, `lease_until`, `renew_before` and `lease_token`. `task_id` is the field that makes a listed claim actionable: a repository claim belongs to no task, so the transport stores the claiming run's own identifier, and the executor groups its holdings by it. `?holder=` narrows the list to one actor; an empty `?holder=` is refused rather than treated as unset, because returning every claim for a caller who meant to narrow it is the silent widening the task listing's own empty-value branch exists to prevent. ⚠️ **The listing deliberately omits the transport key.** The key is this API's business, never the caller's — a caller addresses a claim by `scope` and `id`, which is exactly what the renew and release routes accept, so a listed claim is actionable without the caller learning how it is stored. `skipped` counts refs under the prefix that are not addressable claims — the redrive streak keys are counters, never acquired or released, and answering them as claims would invite a caller to renew something that is not a lock — counted rather than dropped, for the same reason the task index counts unparsable pages instead of coercing them. An expired claim is reported with its stored `lease_until` rather than flagged or omitted: expiry is a comparison against the caller's own clock, and computing it here would bake this server's clock into an answer that goes stale the moment it is sent. The response carries no `index_age_seconds`, unlike the task and goal listings, because claims are read live from git-rest and no index describes them. ⚠️ **This route required the `/`-joined claim key first, and that is not incidental.** Deriving `scope` and `id` from a key is the inverse of the derivation, and under the old hyphen join `claims/repo/a-b-c` could not be split back into an owner and a repo at all — a listing would have returned claims that no caller could address. The ordering is the reason the key repair went first.

## v0.17.0

- fix: **Join the repository claim key with `/` instead of `-`, because the hyphen join silently made two repositories share one lock.** A claim is a mutual-exclusion primitive, and its key has to identify exactly one object. It did not: `repoClaimScope` built `claims/repo/<owner>-<repo>`, and a hyphen is legal inside both components — `validClaimComponent` accepts `[a-z0-9._-]` — so `owner=a-b, repo=c` and `owner=a, repo=b-c` both derived `claims/repo/a-b-c`. Two distinct repositories therefore aliased one lock, which means the exclusion did nothing and two runs could proceed against the same repository believing they held it. The join is now `/`, which cannot collide because `/` is rejected inside a component, and it matches the streak keys (`claims/redrive/<taskid>/<phase>/<n>`), which were already slash-separated. ⚠️ **This is a wire-format change and must be deployed in lockstep with `agent-task-executor`'s `DeriveClaimKey`, which derives the same key from the other side** — the format belongs to the executor, and a period where one side writes `claims/repo/a/b` and the other reads `claims/repo/a-b` is a period where the lock excludes nothing. In-flight claims carry a 5-minute lease, so a rolling deploy orphans each one for at most one lease, and the next acquire takes it over rather than refusing: `acquireToken` (`pkg/handler/claims.go`) reads the existing ref and, when `leaseExpired` holds, returns **that ref's own SHA** as the compare-and-swap token with no live holder, so the acquire succeeds instead of answering `409 claim_held`.

## v0.16.1

- fix: Persist the change-event baseline so a restart no longer skips the commits it missed. `--event-baseline-path` / `EVENT_BASELINE_PATH` names a file that outlives the process, and the feed resumes from the last published commit instead of adopting the current HEAD. Before this the baseline was process-local, so every commit pushed while the process was down was adopted silently and never published: a task's last record stayed at the phase it held when the instance was last up, and the executor drove it at that phase indefinitely. Two paths could drop the range — the restart gap, and a range abandoned after `MaxPublishRetries` — and this change repairs both. The abandoned-range path no longer persists the skip: the publish position moves past the abandoned range so later changes still publish, while the persisted baseline stays before it, so a restart re-attempts the range instead of dropping it for good. Empty keeps the previous process-local behaviour, so the flag is opt-in per instance.

- fix: Retain an abandoned publish range instead of persisting the skip, and classify sarama's client-side oversized-message error as permanent. An abandoned range used to advance the persisted baseline to head, so a range the feed deliberately skipped was dropped durably and a restart resumed past it. The feed now keeps two positions — the publish position, which moves past the range so later changes still publish, and the persisted baseline, which stays before it so a reload re-attempts the range. The abandon log line is replaced rather than supplemented: `abandoned_range_retained range=<from>..<to> baseline=<retained>` names the range and the baseline a restart resumes from, and the old `abandoning changes from … resuming at <head>` wording is gone. Separately, `publisher.IsPermanent` now also classifies a sarama `ConfigurationError`: the producer rejects a message over `Producer.MaxMessageBytes` locally, before the broker sees it, so the error is not a `KError` and was classified transient — one oversized task body reset the retry budget on every tick and blocked every later change forever, never reaching the cap that exists to abandon a poison message.

- fix: Drop a persisted event baseline that names a commit the repository no longer holds. A re-cloned volume, a force-push or a `gc` can leave the stored SHA unresolvable, and `git diff-tree` then fails in a way that is not a broker error — so the feed classified it as transient and retried it forever, and publishing stopped permanently rather than degrading. Startup now resolves the baseline against the repository and falls back to adopting HEAD when it is absent, which is the behaviour every instance had before the file existed. A repository that cannot be read at all takes the same fallback rather than failing startup — the read API stays up — but it is logged as its own cause, so a broken `git-dir` is distinguishable from a baseline that is genuinely gone. Both outcomes do reset the baseline to HEAD on the next publish.

## v0.16.0

- feat: Let `GET /api/v1/tasks` take more than one `task_type`, so a caller whose population spans several types asks once instead of issuing a query per type. `?task_type=a&task_type=b` and `?task_type=a,b` are both accepted, and the values are a **union**: a task matches when its type is any one of them, while every other filter still narrows by intersection. This is what a dedup check needs — `sentry-collector-agent` lists tracked tasks to decide what to create, and its pages carry three different `task_type` values, so a single-value filter returns 1,726 of 1,898 and the missing 172 would be re-created as duplicate tasks on every run. A subset filter there is worse than no filter, because the caller's own guard only catches "matched nothing" and 1,726 is neither empty nor correct. A single value is the one-element case and is unchanged.

## v0.15.0

- feat: Add `job_state` and `pr_state` to `vault_api_open_tasks`, so the four-state split of the open-agent board is derivable from the metric instead of re-derived by every consumer. `phase` alone cannot separate the four: a record marked `in_progress` with no job looks identical to one an agent is working, and nothing in the metric said whether a record's PR had already merged — the two states whose remedies are opposite ("leave it alone" vs "run a closer"). `OpenTaskKey` gains `JobState` and `PRState`; the gauge declares `job_state` and `pr_state` as variable labels; `openTasksByStageTypeAndPhase` becomes `openTasksByState`. **`job_state`, not `job`:** the scrape config supplies its own `job` label (`kubernetes-pods`) and renames a colliding exporter label to `exported_job`, so the series would read correctly on `/metrics` and wrongly in Prometheus. **Absence is a value, never a missing label** — PromQL has no positive matcher for label absence, so an empty `current_job` reports `job_state="none"` rather than dropping the label, and `job_state="running"` means a job was *claimed*: nothing here polls the executor, so a job that died leaves its id behind and still reads running until the next dispatch overwrites it. `pr_state` carries the state a sweep wrote into the record's frontmatter (`open` / `merged` / `closed` / `none`) and `unknown` when no sweep has observed the record yet — `unknown` and `none` are deliberately distinct, because the first means "ask again after the next sweep" and the second "this record carries no PR". **The label is as fresh as the sweep, up to a day**, which is enough for a four-state split and not enough to call it live. `TaskItem` serves `current_job` and `pr_state` so a reader chasing a stuck record gets the job id, not just the fact of one. The addition is additive: existing queries that do not name the new labels keep working, and a pod that has not rolled yet keeps reporting the five-label series until it does.

- feat: Add the typed task-content surface, so a task is read and rewritten by identifier rather than by vault path. `GET /api/v1/tasks/{id}` now serves the whole page — `id`, `title`, the frontmatter as an object and the markdown `body` — where it previously served the listing's flat projection; nothing consumed it, so the shape could change rather than be duplicated. `PATCH /api/v1/tasks/{id}` takes a partial frontmatter update from an allowlist of typed keys and answers `400 unknown_field` for anything else, because accepting an arbitrary key lets a client write fields this API does not model and cannot validate. `status` and `phase` in a PATCH go through the same transition graph the dedicated endpoints use, so a patch cannot reach a state those refuse, and `approved_by`/`approved_at` are refused outright — the approval record is written by the approve endpoint alone. `PUT /api/v1/tasks/{id}/content` replaces the markdown body and leaves the frontmatter block byte for byte as it was; it carries no path, so the caller names a task and hands over that task's body while the server keeps the location, the filename and the serialisation. `POST /api/v1/tasks` creates a task from a title, frontmatter and body, mints a `task_identifier` when the caller supplies none — a task addressable only by its filename stops being addressable the moment someone renames the page — and answers `409 task_exists` on a collision rather than overwriting. A title that cannot be a filename answers `400 invalid_title` instead of being silently rewritten, since a sanitised name is a task the caller cannot find again. The document read goes through the page storage rather than the filesystem, so it increments `vault_api_file_reads_total{kind="page_read"}` — the counter a verification run discriminates on, which a direct file read would leave flat. **A create is not a way around the PATCH rules:** it runs the same allowlist and the same approval refusal, plus `task_identifier`, which only a create may name. It normalises `status` and `phase` and refuses an unknown value, because the index excludes a task whose status does not parse — such a task would answer 201 and then never appear in any listing. A caller-supplied `task_identifier` that another task already answers to answers `409 task_exists` rather than making one of the two unaddressable. The frontmatter block's closing delimiter is matched as a **whole line**, not as the first `\n---`, because YAML allows a block scalar whose lines begin with dashes and a prefix match would cut the real frontmatter in half and move the remainder into the body.

- feat: Make `GET /api/v1/tasks` a typed query that refuses a filter it does not serve. It gains `task_type`, `short_id` and `updated_since` alongside the existing `assignee`, `status`, `phase`, `goal` and `cluster`, and **any other query parameter now answers 400 `unknown_filter`** instead of being ignored — the handler used to drop what it did not recognise and return every task, so a caller whose filter was misspelled or unsupported read the whole vault as its match set and could not tell the filter had been dropped. `updated_since` takes an RFC3339 instant and keeps tasks whose page was modified at or after it; an unparseable value answers 400 `invalid_filter` for the same reason, a declared filter sent with **no** value is refused rather than read as unset — `query.Get` cannot tell `?task_type=` from an absent parameter, so treating it as unset returns the whole vault to a caller who meant to narrow it — and a task whose page reported no modification time is excluded rather than guessed at. The listing also carries `short_id` and `updated_at` per task. This is what retires the collector's filename glob: `* Tasks/Analyze Sentry issue *.md` asks a filesystem question, and the typed question it was standing in for is `?task_type=sentry-deep-analyzer`, or `&short_id=<sentry issue id>` per alert.

## v0.14.0

- feat: Add typed claim endpoints addressed by task identifier or repository, so a claim is a concept in the API rather than a key-value ref store. `POST`, `DELETE` and `GET /api/v1/tasks/{id}/claim` plus `POST /api/v1/tasks/{id}/claim/renew` take a claim on a task; `POST /api/v1/repos/{owner}/{repo}/claim` and its `renew`/`GET`/`DELETE` siblings do the same for a repository. A repository has no task of its own, so its claim carries the claiming run's task identifier — the transport requires one on every ref write. The typed body is `holder` / `ttl_seconds` / `lease_token` and the transport underneath is git-rest's claim refs (`cluster` / `lease_until` / `expected_sha`), which a caller never sees; the lease defaults to 300 s and the response states `renew_before` 60 s ahead of expiry rather than leaving the caller to re-derive it. A lost compare-and-swap answers `409 claim_held` on acquire and `409 lease_lost` on renew or release — the two are different failures and are not collapsed. **An expired lease is free:** git-rest stores `lease_until` and never compares it, so a holder that died would otherwise block the key forever — every later acquire losing the compare-and-swap and answering 409 to a claim nobody holds. Acquire therefore reads the current ref and, when its lease has passed, retakes it carrying that ref's own SHA, so exactly one of several concurrent acquirers wins and the advertised lease is real rather than advisory. The 409 on a live claim now names the holder and its `lease_until`, `renew_before` is stated on the read route too, `ttl_seconds` is bounded at 24 h (above ~9.2e9 s the duration overflows and the lease would render already expired), and a 4xx from git-rest is answered 400 `invalid_claim` instead of 500 — a refused ref name is the caller's mistake, not a server fault. An unknown field in the body answers 400 `invalid_body` rather than being ignored, so a misspelled `ttl_seconds` cannot silently fall back to the default lease. New `pkg/gitrest.RefClient` carries the ref operations, since the existing client could only write whole files. **The repo key is the executor's, not a second spelling of it:** owner and repo are lowercased and joined with a hyphen exactly as the task executor derives them, because the executor is the other holder of these refs and two spellings of one repository would be two locks that do not exclude each other. A name outside `[a-z0-9._-]`, a leading `.`, a trailing `.lock` or a bare `..` answers `404` before any transport call, rather than reaching git-rest and coming back as a caller error.

## v0.13.0

- feat: Add `phase` to `vault_api_open_tasks`, so the open-task count splits by work phase instead of collapsing every non-terminal record into one number. The gauge carried `{stage, task_type}` only, which is why the dashboard showed 43 open `pr-review` records as a single line even though 36 sat at `planning`, 5 at `human_review`, 1 at `execution` and 1 at `in_progress` — four populations whose remedies are different. `OpenTaskKey` gains `Phase`, the gauge declares `phase` as a third variable label, and `openTasksByStageTypeAndPhase` keys on it; a task with no `phase` counts under `PhaseUnknown`, mirroring `StageUnknown` / `TaskTypeUnknown`, so the gauge total still equals the real open count instead of silently dropping unphased pages. **The label carries the normalized phase, never the raw frontmatter string:** the index runs `domain.NormalizeTaskPhase` before storing `Phase`, and that maps the legacy `in_progress` alias onto `execution`, so the gauge emits seven phase values and never both spellings of one phase. The addition is additive — every existing query that does not name `phase` keeps working unchanged, and a pod that has not rolled yet keeps reporting the two-label series until it does.

## v0.12.1

- fix: A task write now patches only the frontmatter keys the handler changed, so an API edit stops re-rendering the whole block. `document.write` called `storage.SerializeFrontmatter`, which re-marshals the entire block from a map and therefore rewrites every untouched key into `yaml.Marshal`'s own key order, indentation and quoting — measured on a `planning → execution` transition, which turned a two-space double-quoted `goals` entry into a four-space single-quoted one. The document now records each change through `set`, and the write path calls `storage.PatchFrontmatter` (vault-cli v0.183.0) with that subset, leaving every other byte of the block intact. Approval, phase and status writes all go through it; `phase`, `status`, `assignee`, `task_identifier` and any key the handler did not touch survive unchanged.

## v0.12.0

- fix: Make `GET /readiness` describe the tree it is serving now, not the last build that succeeded. `Build` set `ready = true` and nothing ever cleared it, so a pod that had built once answered `200 ready:true` forever — measured on sun, whose vault-api reported `{"ready":true,"index_age_seconds":6696,"head":"e8aca81e"}` while its tree sat 111 minutes and 414 commits behind remote `35643048`, because the git-rest puller that used to advance it had been retired. `handleReadiness`'s 503 branch was unreachable dead code. A failed rebuild now clears the flag (the previous index keeps serving, so a read never fails on a transient read error) and the next successful one restores it. **`ready` also requires two freshness signals inside `--stale-after` (default `5m`, ten times the 30 s `--refresh-interval`), because a successful build says nothing about whether the tree still exists in a live state:** `index_age_seconds` is now the age of the last *confirmation* that the index matches the tree — advanced on every refresh tick that finds the HEAD unmoved, not only on a rebuild — and the new `tree_age_seconds` is the age of `.git/FETCH_HEAD`, the puller's heartbeat, since every `git fetch` rewrites it even when it brings nothing new. The two are separate because they fail independently: a rebuild can fail on a live tree, and a tree can freeze under a healthy loop. **The tree signal is the one that catches sun, and it cannot be replaced by an age threshold on the build alone:** a quiet vault whose tree still matches its remote is indistinguishable from a frozen one by any in-pod read of HEAD, and a naive `index_age_seconds > N` rule would have marked the live `vault-api-trading` on nuke dev not-ready at `index_age_seconds: 10357` while its tree matched remote `a4526b15` exactly. `--stale-after=0` disables the rule for a local run against a tree nothing fetches; `tree_age_seconds` is `null` when the tree carries no `FETCH_HEAD` to measure, and that half of the rule is then skipped rather than guessed. **Operational consequence:** `/readiness` is the `readinessProbe` on all three deployments, so a pod whose tree stops being fetched now leaves its Service endpoints after ~30 s instead of serving stale data indefinitely — the point of the change, and the trade it makes. `/healthz` is untouched, so a red readiness never restarts a pod.

## v0.11.0

- feat: Let `POST /api/v1/merge` return the merged bytes instead of writing them. A new optional `apply` field defaults to `true`, keeping the original contract for a caller with no working tree of its own; `apply: false` answers `{"result":"merged","content":…}` and writes nothing. git-rest must send `false`, because it calls from inside its own pull holding the repository mutex: asking it to write back through its own API waits on the lock the pull already holds, and the request never returns — measured locally, the client timed out at 30s with vault-api's handler still blocked on the write. The `pull: merged` marker now comes from `LogResolvedMerge`, shared by both paths, so the puller's automatic path is not silent just because the writing moved to the caller.
- feat: Attribute every `POST /api/v1/merge` request to its caller in the log. The handler emits one `merge: caller=<git-rest|manual> path=<path>` line before the merge runs, read from an `X-Merge-Caller` header that names the puller. Only the literal `git-rest` is recognised; an absent header or any other value is reported as `manual`, because the header is not a credential — nothing it carries may claim the automatic path — and an unrecognised value is never echoed into the log. A quarantined request is attributed too, so the automatic path stays visible exactly when it declined to act. This is what lets a probe tell a reconciliation the service performed on its own from one an operator staged with curl.

## v0.10.0

- feat: Add `--event-vault-name` / `EVENT_VAULT_NAME`, the vault slug stamped on task change events as `lib.Task.Vault`. It is separate from `--vault-name` because the two are different identities: `--vault-name` is the display name the read API reports, while the event field is the routing key a consumer compares against its own vault. Before this, an instance whose display name differs from its routing slug stamped the display name, and every task it published was dropped as foreign by the executor that owns it (`skip task <id>: foreign vault vault=<display> task_vault=<slug>`) — the task was never spawned. Empty falls back to `--vault-name`, so an instance where the two coincide is unchanged.

## v0.9.0

- feat: Add `POST /api/v1/merge`, the production caller of `ResolveDivergedPull`. It takes the three sides of a diverged file — `base`, `ours` and `theirs`, each with its committer time — resolves them per frontmatter key and writes the merged bytes through git-rest, answering `{"result":"merged"}` or `{"result":"quarantined","reason":…}`. The seam had shipped since v0.6.0 with no caller, so no running path ever invoked the merge; the endpoint supplies one without making `vault-api` a puller, which it is not — git-rest pulls and the refresh loop only compares HEAD.
- feat: Log one `pull: merged` line per genuinely reconciled file, naming the path and both sides' committer times, so a merge the API performed is distinguishable from one git-rest resolved on its own. The line is emitted only when both sides changed relative to the base and only after the write succeeds: a quarantined merge, a fast-forward and a failed write each log nothing, so the marker cannot be satisfied by an unconditional log.
- fix: Confine `POST /api/v1/merge`'s client-supplied `path` and give the route its own body cap. The path is refused when it carries a `..` segment, a control character, a leading `/` or surrounding whitespace: it becomes both a git-rest URL segment and part of the log line, and `url.PathEscape` leaves dots unreserved, so `..` would otherwise survive into the outbound URL. The cap is 32 MiB rather than the write endpoints' 64 KiB, which was chosen for a phase name and an approver and cannot hold three file contents. **This route also refuses to run when `GATEWAY_SECRET` is empty** (503 `merge_requires_gateway_secret`) instead of inheriting the group's "empty secret = no auth" contract: it writes caller-supplied content to an arbitrary vault-relative path, a strictly larger blast radius than the other write endpoints, which resolve their target through the index and enforce the phase and status graphs.

## v0.8.0

- feat: Publish a task change event from every successful write, so `vault-api` becomes the producer the executor's compacted task view reads. The three write handlers publish through `pkg/publisher.TaskPublisher` after git-rest accepts the file — at the single `document.write` chokepoint, so no handler carries its own copy. A publish failure is logged and the request still answers 200: the file is already in git, an error would make the client retry a transition that is now applied, and the pull path publishes the same change from the commit diff. `--kafka-brokers` / `KAFKA_BROKERS` enables the producer and `--topic-prefix` / `TOPIC_PREFIX` selects the per-cluster topic; both are optional, and unset means publishing is disabled while reads and writes are unaffected. The producer is built off the startup path behind a `publisher.Deferred` handle that **both** the write handlers and the pull feed share, so an unreachable broker cannot delay the read API and one change is published once: publishes report a not-ready error until construction succeeds. On the request path a publish is bounded by a 5 s timeout and runs under `context.WithoutCancel`, so neither a broker that goes away after startup nor a client hanging up can hold open or cancel a response that is already decided. With no brokers configured the handle holds a discarding publisher, so a deliberately disabled producer does not log an error on every successful write.

## v0.7.0

- feat: Detect changes vault-api did not write itself and publish one change event per changed task file. The refresh loop diffs the previous HEAD against the current one with `git diff-tree` — not `git diff`, because the vault volume is mounted read-only and `git diff` refreshes the index — and hands every added, modified or deleted `25 Tasks/*.md` to the `TaskPublisher`. A deletion is read from the old commit, so its tombstone keeps the identifier the file actually carried instead of a slug guess. A pull that touches only goals emits nothing, and the HEAD baseline advances only after a batch publishes, so a Kafka failure retries the same diff rather than dropping it. This is the pull-side producer that must exist before the controller's git scan can retire.

## v0.4.0

- feat: Add `pkg/publisher`, the producer half of the task change-event stream. `TaskPublisher` publishes one `lib.Task` record per task id onto `{prefix}-agent-task-v1-event` through `cdb.EventObjectSender` with `lib.TaskV1SchemaID` — so the topic name is derived from the schema, never assembled by hand — and a tombstone on delete. The interface takes only a context and a task, so the typed write handlers and the pull path that detects externally pushed changes can both call it.

## v0.3.0

- feat: Add `MergeFile`, a three-way per-key frontmatter merge for a diverged vault file. A key only one side changed is kept; a key both sides changed follows its field class — validated lifecycle transition for `status`/`phase`, larger integer for counters, order-preserving union for append-only lists, concatenation for `metrics_sessions`, later committer time otherwise. A body both sides edited differently quarantines with a named reason instead of being concatenated.
