# Changelog

All notable changes to this project will be documented in this file.

## v0.35.0

- feat: **`GET /api/v1/tasks` carries `task_identifier_previous`.** `TaskItem` projected the current identifier (`ID`) but not the predecessor a re-addressed page records, so a consumer holding only the listing could answer "which file carries this identifier" for the current key and never for the alias. The field is projected from frontmatter like the other board fields and is empty when the page was never re-addressed — an absent predecessor stays distinguishable from an empty one only in that both mean "no alias".

## v0.34.4

- fix: **a goal or topic edit is applied in place instead of rebuilding the whole index.** `applyOneEvent` took the incremental path only for task events, so a goal or topic file change fell through to a full `Index.Build` (~37s on private-personal, serialized behind other rebuilds) and a goal flag/unflag showed 60-75s late. It now reads the page and calls the new `Index.UpsertGoal` / `Index.UpsertTopic`, which share their item projection with `Build`; deletes still rebuild.
- fix: **an attached vault (`-multi-vault`) now refreshes when its page files change, not only when its git HEAD moves.** A frontmatter edit written out of band (vault-cli, the vault-ui flag toggle) stayed invisible until git-ai-sync committed it (~1-2 min) plus the next 30s tick. Each attached tick now also reads a cheap fingerprint of the tasks/goals/topics directories (newest `*.md` mtime plus file count; `ReadDir` + stat, no file reads, no filesystem watch) and rebuilds when it moved, alongside the existing HEAD check.

## v0.34.3

- fix: carry assignee and priority on the goal list projection. `GET /api/v1/goals` (and `/api/v1/topics`) now serve the page's `priority:` as an integer (0 when absent, always emitted like the task projection) next to `assignee`, so vault-ui v0.113 goal cards no longer lose assignee/priority when the board reads goals from vault-api.

## v0.34.2

- fix: **`GET /api/v1/goals` and `/api/v1/topics` carry `phase`, so the board can group goal and topic cards into phase columns like tasks.** `GoalItem` and `TopicItem` were written for the flagged-row consumer and never carried the page's `phase:`; the board groups cards by `item.phase`, so every goal and topic landed in the `—` column and the six phase columns stayed empty. Measured 2026-11-23 against the live `:9091`: `/api/v1/goals` returned 511 items and `/api/v1/topics` 30, none with a `phase` key, while all 421 `24 Goals/*.md` and 23 `23 Topics/*.md` declare one. The field is carried raw, matching the goal/topic convention (`GoalFrontmatter.Phase` preserves legacy and hand-typed values), and the board maps `in_progress` onto the `execution` column client-side.

## v0.34.1

- fix: bump `github.com/bborbe/agent` so the task-frontmatter allowlist admits `created`. Since v0.34.0 the create/patch allowlist is `lib.TaskTypedFields()` ∪ `lib.TaskPipelineFields()`, and `created` was in neither — so `recurring-task-creator`'s AI Knowledge Sharing template, which stamps `created: "{{current_date}}"` for vault-cli's closure gate, had every create refused `400 unknown_field field=created` and dropped whole. Measured 2026-11-22/23 on `agent-task-controller-seibert-personal-0`; the weekly instance never materialized. The pinning test now exercises the key through a real PATCH.

## v0.34.0

- feat: **`-multi-vault` (`MULTI_VAULT=true`) serves every task-bearing vault in vault-cli's config on the list endpoints, the way vault-ui serves every configured vault — so a flagged `seibert-*` goal or task is no longer invisible to the claude-wrapper flagged tick.** Until now an instance indexed exactly one vault (`VAULT_PATH` / `VAULT_NAME`), and the local instance the flagged tick reads ran with `VAULT_NAME=private-personal`: `GET /api/v1/goals?flag=true` returned 13 rows, all `private-personal`, so every operator-flagged goal and task in another vault was dropped before the tick saw it, with no error and no log line. In multi-vault mode vault-api reads `~/.config/vault-cli/config.yaml` (or `-vault-cli-config`), builds one read-only index per vault that declares a `tasks_dir`, and merges them into `GET /api/v1/tasks`, `/goals` and `/topics`, each row carrying its own `vault`. `GET /api/v1/tasks/{id}` resolves a task the primary vault does not hold in the attached vaults and reads it from that vault's own tree — the flagged tick reads every listed task's detail, and one 404 there fails the whole tick. Every other lookup by id, every write and every change event stays with the primary vault, so no write can land in the wrong vault. A vault whose index cannot be built is logged as `vault=<name> rows_source=unavailable` and listed under `/readiness`'s new `unavailable_vaults`, while every other vault keeps returning its rows. Attached vaults refresh on the git-HEAD check, never the filesystem watch: on macOS the watch holds one descriptor per file, and watching every vault exhausted the descriptor limit so the HTTP server stopped accepting connections. Off by default — cluster deployments keep serving their one vault unchanged.

## v0.33.1

- fix: **`POST /api/v1/tasks` and `PUT /api/v1/tasks/{id}/content` no longer share the 64 KiB write-endpoint body cap, so a task whose rendered body is a whole document can be created.** `maxWriteBodyBytes` was sized for "a phase name, a status name and an approver", and both routes that carry an entire markdown body inherited it. A recurring task's rendered template routinely runs past it — the `rebuild-nuke-cluster` schedule's body is ~199 KB — so every create for it was answered `400 invalid_body: http: request body too large`, the task never materialized, and the only witness was one 400 in the consuming controller's log. The failure was not schedule-specific: `agent-task-controller-openclaw-0` logged five of the same 400 in a 48-hour window. Both routes now use `maxTaskBodyBytes` (4 MiB), leaving room for a long task document while staying far below `maxMergeBodyBytes`; the small write endpoints keep `maxWriteBodyBytes` unchanged.

## v0.33.0

- feat: **`GET /api/v1/tasks` carries the fields the board renders — `blocked_by`, `priority`, `due_date`, `planned_date`, `claude_session_id`, `jira`, `mode` and `open_questions` — so a consumer can serve the board from one list request instead of one detail call per row.** The projection carried 13 keys while the board renders nine more, which left a consumer choosing between a rendering regression and an N+1 over the whole vault; `GET /api/v1/tasks/{id}` has the missing values but only one page at a time. The new fields are projected from frontmatter the page index has already parsed, so carrying them costs no additional read: `open_questions` comes from the index's pre-parsed `Entry.OpenQuestions` on the full build, and the incremental `UpsertTask` path parses the same section from the body it already holds so the two indexing paths still describe a page identically. The two list-valued fields are always `[]` rather than `null` and the optional scalars are always present (`null` when absent), so a consumer never has to tell "absent" from "empty"; the dates use vault-cli's own rendering (`YYYY-MM-DD`, or RFC3339 when the value carries a time).

## v0.32.0

- fix: **the task PATCH allowlist is imported from `github.com/bborbe/agent` instead of kept as a copy here, so one new write-only field can no longer cost a whole result write.** `fieldRefusal` now asks `lib.TaskPatchFieldAdmitted`, the same rule `agent-task-controller` calls, and the local `typedTaskFields`, `agentPipelineFields` and `metricsFieldAdmitted` definitions are gone. The class is the one measured on 2026-11-20 19:52 on `agent-task-controller-personal-0`: a result carrying `run_claim` answered `400 unknown_field`, was retried three times, acked, and dropped, with the page left in its pre-run state. A copy per repository is what let the two drift — the controller's denylist fell one field behind the schema. `max_retries` is the one key this release newly admits (it rides a result PATCH as an operator-set value); `run_claim` stays refused, because it is a spawn-gate marker with no producer and a result write must not set it. Removing a key from the shared definition now fails `make test` naming that key.

## v0.31.0

- feat: **`GoalItem` and `TopicItem` carry `role`, `mode`, `defer_date`, `blocked_by` and `flag_set_by`, so a flagged goal or topic can be enriched from the list projection alone.** Without them a consumer that selects flagged rows had only the task rule available: it either read the page itself — which is what the index exists to prevent — or silently applied the task defaults, so a goal deferred to the future opened its manager early and a goal's own `role` was ignored. These are the same five fields a task's record endpoint already serves; goals and topics now match.

## v0.30.0

- feat: **`GET /api/v1/goals` and `GET /api/v1/topics` serve a `flag` filter, `GoalItem`/`TopicItem` carry `flag` and `claude_session_id`, and `GET /api/v1/topics/{id}` resolves one topic.** Without these a goal's flag and its recorded manager session were invisible to every API consumer, which is why claude-wrapper's flagged tick had to parse goal pages itself; with them the tick can ask the index instead. The two list endpoints previously read no query string at all, so `?flag=true` silently returned every row — they now refuse an unsupported parameter with `400 unknown_filter` and an empty one with `400 invalid_filter`, matching `/tasks`, rather than widening a result the caller believed it had narrowed.

## v0.29.1

- fix: **a local-mode edit is applied to the one changed page instead of rebuilding the whole index, so freshness stays inside the 5 s budget on a large vault.** A full `Build` over the private-personal vault's 13k pages takes ~16 s — measured 16.3 s end-to-end on the bootstrapped instance — which misses the freshness target. The watcher now routes a task create/modify to `ReadPage` + `UpsertTask` and keeps the coalesced full rebuild for deletes and goal/topic edits, where no incremental path exists. A failed page read falls back to the rebuild rather than dropping the change.

## v0.29.0

- feat: **a local mode (`--watch` / `WATCH=true`) drives the index from a filesystem watch instead of the git-HEAD check, so a laptop instance serves an edit within a second with no commit.** The cluster path rebuilds only when HEAD moves, which on a laptop lags every edit by git-ai-sync's interval — a row flagged or deferred a minute ago stays invisible until a commit lands. In local mode the refresh loop consumes the shared library's watcher (`vault-cli/pkg/ops.WatchOperation`, fsnotify + debounce — no forked watcher) and rebuilds the index on each debounced change, coalescing a save's event burst into one rebuild. A 10× periodic full rebuild bounds how long a missed filesystem event can leave the index stale, and the readiness heartbeat (`index.Verify`) still runs. The git-HEAD gate is bypassed only in this mode; the cluster path is unchanged. The change-event feed still advances on each rebuild, so a local instance's baseline keeps moving.

- feat: **`GET /api/v1/tasks` serves `flag` and `due` filters, and `GET /api/v1/topics` serves the topic pages alongside tasks and goals.** `flag=true|false` keeps tasks whose frontmatter flag matches, and a non-nil pointer keeps "unset" distinct from `flag: false`. `due=now` keeps tasks whose `defer_date` is absent or at or before the injected clock — the boundary is inclusive and pinned by a test. Both filters are declared in the allowlist, so a misspelled or unsupported value answers `400 invalid_filter` and an unknown parameter still answers `400 unknown_filter` rather than silently widening the result to every row. `TaskItem` now carries `defer_date`. Topics are read from `TOPICS_DIR` (default `23 Topics`) through the same page index; a missing directory serves an empty list rather than failing the build.

- fix: **the local-mode watcher goroutine is joined and its error logged instead of dropped, and `/api/v1/topics` answers an empty JSON array (not `null`) when the topic directory is absent or `TOPICS_DIR` is empty**, matching the `[]` shape every other list endpoint guarantees. `/readiness` now counts topic warnings alongside task and goal warnings. `GET /api/v1/topics` is also restricted to GET.

## v0.28.0

- feat: carry an optional `spawned_at` on the claim routes, so a peer that takes an expired claim over can tell a holder that created its Job from one that only held the key. Accepted on renew only — an acquire drops it, because a marker at acquisition would assert a Job that does not exist yet — and a renew that names none keeps the stored value, so the holder's own 60 s renewal loop cannot erase it. Surfaced on `GET /api/v1/tasks/{id}/claim`, on the write responses and on `GET /api/v1/claims`. Additive and omitted when unset, so an older reader is unaffected.

## v0.27.2

- fix: **every `metrics_`-prefixed frontmatter key is accepted, so a prototype run's `## Data` and `## Result` reach their page again.** `agentPipelineFields` is a closed set, and `fieldRefusal` refuses the *whole* read-modify-write patch on the first unknown key — so each new counter the strategy-prototype agent's run record carries cost the entire delivery, not just that counter. `run_id` and `metrics_runs` were enumerated in v0.27.1 as the 2026-11-17 instance of this class; six more keys (`metrics_agent_turns`, `metrics_interaction_count`, `metrics_input_tokens`, `metrics_output_tokens`, `metrics_cache_read_tokens`, `metrics_cache_creation_tokens`) were still refused. Measured 2026-11-18 on dev vault-api v0.27.1: 240 `unknown_field` attempts in 24 h across those six keys, every one a run that completed and could not write its page. The fix is the `metrics_` **prefix** rather than six more lines, because the key list lives in `agent-task-controller` and `agent-task-executor` and a new counter there must not need a vault-api release before a verdict can be published. The namespace is narrow: a non-`metrics_` unknown key is still refused `400 unknown_field`, so the drift control both allowlists exist for survives, and the near misses (`metrics`, `metricsx_…`, `unseen_metrics_x`) are pinned by test.

## v0.27.1

- fix: **`run_id` and `metrics_runs` are accepted, so a prototype run's `## Result` and `## Ledger` can reach its page at all.** The strategy-prototype agent's delivery carries `run_id` (its own re-run guard) and `metrics_runs` (the controller's transcription of the run's per-variant metrics); `agentPipelineFields` carried neither, so the whole patch was refused and the page kept its pre-run state. Measured 2026-11-17 on the dev stage: three prototype runs each parked `status: completed` / `phase: done` with **no `## Result` and no `## Ledger`** — `patch attempt 1 of 3 failed … 400 unknown_field field=run_id`, then `field=metrics_runs`. The frontmatter transition landed and the body was dropped with it. Both keys are stored and carried, not interpreted.

## v0.27.0

- feat: **`GET /api/v1/tasks/{id}?ref=<ref>` serves the task as it exists at that ref, so a caller can tell a landed write from one still sitting in the working tree.** A write reaches the working tree the moment vault-api accepts it, while the commit that carries it lands on git-rest's cadence — so a caller verifying "did this land" against the ordinary read is answered by the write path's own echo, and would report success for a write that never committed. The ref-qualified read resolves the id through the same index and then reads the page with `git show <ref>:<path>` (the existing `Differ.ReadAt`), so the answer comes from the committed history. **The error split is load-bearing:** a ref that resolves but does not carry the path answers `404` — the ordinary not-committed-yet state, which a waiting caller must treat as "not landed" — while an unresolvable ref answers `500`, because a mistyped ref name would otherwise make every write look dropped. `ErrNotAtRef` carries that distinction, and `ReadAt` decides it by re-checking the ref with `Exists` only on the failure path. Additive: no `ref` keeps today's working-tree read byte-for-byte. **The ref is validated before it reaches git, and `git show` runs with `--end-of-options`:** a ref arrives from a query string, and git parses a leading `-` in argument position as an option — `--output=<path>` makes `git show` create or truncate a file, so an unvalidated value would have been a file-creation primitive rather than a ref. A ref outside the ref-safe character set now answers `400 invalid_ref`. The not-at-ref classification is also narrowed: only a ref that resolves *and* whose tree lacks the path answers `404`, so a corrupt object or an unreadable repository stays a `500` and is never reported to a waiting caller as "not landed". The 500 body carries a fixed reason instead of `err.Error()`, which would have echoed git's argv and the vault's on-disk paths. The five new specs run against a real git repository, including a leading-dash ref (asserting `400` and that no file was created) and a tag ref (proving a non-HEAD ref is served).

Build-time file reads now count as `page_read` rather than `page_list`.

## v0.25.0

- feat: **every working phase (`planning`, `execution`, `ai_review`) may transition to `done`, so the executor's succeeded park can close a record.** `PublishParkSucceeded` writes `status: completed` + `phase: done` from the phase a Job succeeded at and never advanced; `phaseEdges` allowed `done` only from `human_review`, and the executor treats `human_review` as terminal (`terminalPhases`), so the park never evaluates it and the write was refused `invalid_transition: planning -> done` on every phase the park could act on — measured 2026-11-17 on `vault-api v0.23.1` + `agent-task-executor v0.64.2`. ## v0.24.0

- feat: **`POST /api/v1/tasks/{id}/readdress` accepts an optional `previous` field, so a repaired identifier still answers to the address it replaced.** The controller's scanner mints a fresh `task_identifier` for a file whose old one was missing or invalid, and writes the replaced value as `task_identifier_previous` in the same frontmatter edit; `result.FindTaskFilePath` matches on either key, so a result already in flight under the old address still reaches the file rather than resolving to nothing. The typed route could not express that half — `task_identifier_previous` is in neither `typedTaskFields` nor `agentPipelineFields`, and `PATCH` refuses it — so porting the scanner onto the typed surface would have silently dropped the mechanism behind `bborbe/agent-task-controller#127` on the one stage where the repair runs (`AUTO_INJECT_TASK_IDENTIFIER` is `false` on dev, `true` on prod). **Additive and optional:** a request that omits `previous` produces exactly today's file, `previous` equal to the new address is ignored, and a re-send of an already-applied move still records it so a retry cannot lose the in-flight identity. Both keys land in one patch, so there is no window where neither address resolves.

## v0.23.0

- feat: **PATCH accepts a `body` key, so a caller can change frontmatter and body in one commit.** `document` carried only the parsed frontmatter and the subset of changed keys, and `set()` routes everything into frontmatter — so a `"body"` key would have been written as a *frontmatter field literally named body* and left the real body untouched. The controller's planning retry is the motivating caller: it appends a `retry n/3` bullet to the body **and** bumps `planning_retry_count`/`phase`, and the typed client splits those into `PatchTask` (fields) and `PutBody` (body), so the port would have been two non-atomic writes where git-rest did one. Now `body` is lifted out of the request before the field loop, held on the document, and the rendered content is the **original frontmatter block byte-for-byte** plus the new body — passed to the existing `storage.PatchFrontmatter`, so the write stays one commit and still patches only the keys in `changed` (re-serialising the frontmatter would re-render keys this handler never touched). A non-string `body` answers 400 `invalid_body`; an absent `body` leaves the file byte-identical to today's behaviour.

## v0.22.9

- fix: **every frontmatter key the agent pipeline writes is accepted, so a spawn patch lands whole.** `agentPipelineFields` was still short of the pipeline's own set: the executor's spawn-time `update-frontmatter` clears `last_result_status` in the same patch as `current_job` and `claude_session_id`, and the controller's complete-task and auto-supersede patches send `completed_date`, `processed_at` and `superseded_by`. `fieldRefusal` refuses the whole patch on the first key absent from the allowlist, so the spawn of a probe that ran and completed (`metrics_agent_turns: 1`, `## Result` present) carried no `claude_session_id` at all — measured 2026-11-12T19:28:49Z on `agent-task-controller-personal-0`.
  ⚠️ **The log undercounted the set, as it always does.** In the same 48-hour window the dev controllers logged only `claude_session_id` (71×) and `last_result_status` (9×), while `completed_date`, `processed_at` and `superseded_by` were equally absent and had simply not fired — no complete-task or supersede command had run. `fieldRefusal` names one key per attempt and Go map iteration is random, so a log samples this set but cannot enumerate it; this widening came from the producers' source instead. `task_content_allowlist_internal_test.go` asserts every controller/executor-emitted key is writable and every pipeline-only key has a recorded producer, so a key added to one list without the other fails the build; a producer that starts writing a new key is still transcribed there by hand.

## v0.22.8

- fix: **a task patch carrying `claude_session_id` is accepted, so a spawn's `current_job` lands with it.** `agentPipelineFields` is a closed allowlist and `fieldRefusal` refuses the whole patch on the first key absent from it. The controller's spawn-time `update-frontmatter` sends `claude_session_id` and `current_job` in one patch, so the refusal on the session key dropped `current_job` with it — and the task file kept neither field. Measured 2026-11-12 on dev: 22 refusals on `agent-task-controller-personal-0`, every one naming `claude_session_id` and none naming `current_job`, which is what a whole-patch refusal looks like from the log. The key is added beside the other spawn fields; the drift control is unchanged — a key in neither set is still refused wholesale with `400 unknown_field`.

## v0.22.7

- fix: **a probe record that parks non-terminal is re-driven by its next tick instead of refused.** `handleCreateTask` refuses any create whose title path is held by a non-terminal occupant — correct for two attempts sharing an identity, wrong for a probe, which is re-issued on every tick with the *same* identifier. A probe record that parked (`phase: human_review`, `status: in_progress`) therefore answered `409 title … occupied` forever, and the tick's paired `update-frontmatter` failed with it, so both halves of the write path were refused while the lane went on reporting healthy. Measured 2026-11-11: `probe-service-analysis-agent-dev` (`791b703e-…`) parked, every later tick refused at `15:06:35Z`. A non-terminal occupant whose `task_type` is `healthcheck` **and** whose `task_identifier` equals the one the request carries is now reopened in place, exactly as a terminal occupant already was. The identity guarantee is the identifier test: a different identifier at the same path still answers 409, a create carrying no identifier still answers 409, and a live occupant of any other `task_type` is untouched. The recurring-task carve-out is unchanged — it lives in the controller and is keyed on terminal status.

## v0.22.6

- fix: **two appends a blank line apart now merge instead of quarantining.** `mergeBody`'s append test was a strict byte prefix (`strings.CutPrefix`), so a side whose copy of the common body differed only by blank-line placement — which the vault writer normalises — failed the test and quarantined. Measured on the 2026-11-02 OpenClaw incident's own 21 conflicted files: all 20 mixed-shape files still quarantined on v0.22.5 with `body conflict outside the frontmatter`, and comparing with blank lines and trailing spaces ignored showed all 21 were appends. The comparison now falls back to line-wise, blank-line- and trailing-space-insensitive matching; a rewrite, a deletion or a mid-body edit still quarantines.

## v0.22.5

- fix: **a task is readable by identifier immediately after the create that wrote it.** `handleCreateTask` wrote the file and answered 201, but the read path resolves identifiers through the in-memory index, and the index was rebuilt only when the working tree's HEAD moved on the refresh ticker. A caller that created a task and then addressed it therefore got a 404 for a task that existed, for up to one refresh interval. Measured on dev 2026-11-09: `agent-task-executor`'s probe publishes `create-task` and `update-frontmatter` back to back, the update ran 4 ms after the create, and it was dropped with `update-frontmatter: task not found`. `Index.UpsertTask` now records the task a create or reopen wrote — through the same `taskItem` conversion a full build uses, so the two cannot describe one task differently — and both create arms call it with the bytes that landed. It does not make the read path lenient: nothing is recorded for an identifier no file carries, so a genuine miss still answers 404.

## v0.22.4

- fix: **a create that reopens a terminal task is no longer refused by the identifier-uniqueness guard.** `prepareCreateFrontmatter` rejected any caller-supplied `task_identifier` the index already resolved, and the reopen route reaches it carrying the *occupant's own* identifier — so the page being replaced counted as a duplicate of itself and every reopen answered `409 task_exists` naming the identifier the caller had just sent. The answer is indistinguishable at the caller from "the title is occupied", which is what the controller reports, so a probe re-creating the record it owns could never get past it: measured 2026-11-09 on nuke prod, all 17 `-prod` probe lanes were refused inside one 27-second window — only three failure lines reached the log, because that line passes the result sender's 10-second rate sampler — while every record stayed at its 2026-10-26 state. The page at the target path is now exempt, because that write replaces it; an identifier carried by a *different* page is still refused, which is the collision the guard exists for.

## v0.22.3

- fix: **a body both sides appended to after a common base now merges to the union instead of quarantining.** `mergeBody` compared whole body strings, so it could not tell "different" from "conflicting" — two writers appending different sections to one vault file quarantined even though the sections did not overlap and both belonged in the result. The two appended suffixes are now concatenated, ordered by committer time so two nodes merging the same divergence write identical bytes rather than mirror images that re-quarantine on the next sync. A strict prefix takes the longer side, so a shared section is never written twice. A rewrite, a deletion, a mid-body edit, and a frontmatter lifecycle contradiction all still quarantine — `mergeKeys` keeps running first, so a genuine contradiction is never resolved by a body rule.

## v0.22.2

- fix: **the pull emitter tombstones a task's previous event key when a modified file changes its identifier** (a slug-addressed file gaining a `task_identifier`, or a `readdress`), so a compacted consumer view no longer keeps a ghost under the old key. Every tombstone in a batch now goes out before any upsert, so a rename or an identifier swap cannot drop a live task.

## v0.21.0

- feat: **`POST /tasks` can replace a terminal task in place, and a new `POST /tasks/{id}/readdress` moves a task's identifier without moving its file.** Both exist for the controller's remaining call sites, and both were blocked on capability rather than effort: the create route answered `409` for every occupant and had no branch for a terminal one, and `PATCH` refuses `task_identifier` by design, so a retry that mints a new identifier had no route at all.
  **`"reopen": "terminal"`** is opt-in and covers exactly one case — an occupant whose status is `completed` or `aborted`. Absent or any other value keeps the route's original behaviour, so no existing caller changes. ⚠️ **A reopen REPLACES the frontmatter and the body rather than merging them**, and that is why it is a mode on create rather than a read-then-`PATCH`: `PATCH` merges an allowlist, so a reopened task would keep the previous attempt's `completed_date`, `recovery_sha`, `superseded_by` and terminal `phase` — a live task wearing a dead task's history. A **live** occupant is still `409` even when `reopen` is asked for, because reopening one would let two attempts share an identity.
  ⚠️ **The `409 task_exists` payload now names the occupant:** it gains `task_identifier` and `status` beside the existing `id` and `path`. `id` deliberately keeps its old meaning (the title) so an existing caller is unaffected — but as the title is the address the caller just sent, it told them nothing, and they could not tell "same task, terminal, reopen" from "different task, disambiguate the title" without a second read they had no address for.
  ⚠️ **The occupant is resolved by PATH, never through `index.GetTask(title)` — and that is a data-loss fix, not a style choice.** That lookup is one shared address space (identifier, name and slug all resolve there), so a page elsewhere carrying `task_identifier: Alpha` wins it over the task that actually occupies `Alpha.md`. Reachable through the API in three calls: create `Bravo` with `task_identifier: Alpha` (its file is `Bravo.md`, so nothing collides), create `Alpha` with `task_identifier: task-1`, then reopen `Alpha` — the index answers with `Bravo`, its terminal status authorises the reopen, and a `200` replaces the **live** `Alpha.md`. The occupant is now read from the page at the path about to be overwritten, which cannot be shadowed; a spec reproduces the exact three-call sequence and fails if the lookup regresses.
  **`POST /tasks/{id}/readdress`** takes `{"task_identifier": "<new>"}` and rewrites the identifier in place. It exists because the PATCH refusal is right and the retry's intent is legitimate, so the change gets its own auditable verb instead of riding in on an ordinary field write. ⚠️ **Its cost is real and stated:** the old identifier stops resolving for every caller holding it, so it answers `409` when the target identifier is already taken — silently merging two tasks into one address is the worst outcome available here.
  Also lifts the terminal-status predicate into one `IsTerminalStatus`, used by both the index and the create route, so the two can no longer drift.

- fix: **the re-address route now announces the new address, and three edge cases around occupant identity are closed.** The change event is published by `persist`, and its `TaskIdentifier` is read from the item — so assigning the new id *after* the write emitted an announcement carrying the **old** address, the single value a caller must not be told after a move. The assignment now happens before `persist`. Also: the occupant's status is normalised with `domain.NormalizeTaskStatus` before `IsTerminalStatus`, so this branch and the open-task gauge compare the same domain value rather than a raw string and a normalised one — an unreadable status normalises to `""`, which is not terminal, so it can never authorise replacing itself. A re-address to the task's own title or slug is a no-op rather than a `409` naming the task itself (`GetTask` keys identifier, name and slug in one map, so the task resolves back to itself). And the `409` omits `task_identifier`/`status` when the occupant genuinely has none, instead of advertising the string `"<nil>"` — the misleading payload the refusal exists to replace.

## v0.19.0

- feat: **Serve a per-pull-request claim, so two reviews of one repository can run at once instead of queueing behind each other.** The repository claim serialises every review of a repository: `pr-reviewer` takes the repo key, and a second PR's review waits behind the first for as long as it renews — a review that is slow for a legitimate reason blocks every sibling PR in that repository. The new routes are `/api/v1/repos/{owner}/{repo}/pulls/{number}/claim` plus `/renew`, `DELETE` and `GET`, returning `scope: "pr"` and `id: "owner/repo/<number>"`. The executor already derives this key (`DeriveClaimKeysWithBody`) and holds it **alongside** the repository claim, recovering the pair by task id; until now vault-api had no typed route for it, so a caller could list a `pr` claim that no route could act on. ⚠️ **The derivation reproduces the executor's exactly, including two details that look like accidents and are not:** owner and repo are lowercased but the number is **not** (the executor lowercases only the first two, and the number comes from the PR body validated as-is — lowercasing it here would accept an input the executor rejects and split the key space), and the number is validated as a **claim component**, not parsed as an integer (the executor runs `validateClaimComponent` over it, so a stricter integer check would refuse a key the executor can write). ⚠️ **A latent defect was fixed on the way, and it would have failed silently.** The transport requires a `task_id` on every ref write, and `claimTransportTaskID` decided it with `scope != "repo"`. Adding a third scope would therefore have sent the claim's own address, `owner/repo/7`, to git-rest as a task id. Nothing would have errored: the claim would be written with a task id that is not a task, and the executor's recovery pairs a repository claim with its per-PR claim **by task id**, so the pair would have read as two unrelated singles — each then adopted, fenced or released on its own. The test that pins this asserts the transport receives the caller's task id and specifically not `owner/repo/7`.

## v0.18.0

- feat: **Serve `GET /api/v1/claims`, so a caller can ask which claims exist instead of having to know every key in advance.** Until now the claim surface was readable only one object at a time — `GET /api/v1/tasks/{id}/claim` and `GET /api/v1/repos/{owner}/{repo}/claim` — which cannot answer the question a restarting executor actually asks: *which claims do I already hold?* Without that answer the executor cannot see the refs it left behind, so it waits out every lease instead of re-adopting or fencing its own work. The route lists the whole `claims/` namespace in one call and returns, per claim, `scope`, `id`, `holder`, `task_id`, `lease_until`, `renew_before` and `lease_token`. `task_id` is the field that makes a listed claim actionable: a repository claim belongs to no task, so the transport stores the claiming run's own identifier, and the executor groups its holdings by it. `?holder=` narrows the list to one actor; an empty `?holder=` is refused rather than treated as unset, because returning every claim for a caller who meant to narrow it is the silent widening the task listing's own empty-value branch exists to prevent. ⚠️ **The listing deliberately omits the transport key.** The key is this API's business, never the caller's — a caller addresses a claim by `scope` and `id`, which is exactly what the renew and release routes accept, so a listed claim is actionable without the caller learning how it is stored. `skipped` counts refs under the prefix that are not addressable claims — the redrive streak keys are counters, never acquired or released, and answering them as claims would invite a caller to renew something that is not a lock — counted rather than dropped, for the same reason the task index counts unparsable pages instead of coercing them. An expired claim is reported with its stored `lease_until` rather than flagged or omitted: expiry is a comparison against the caller's own clock, and computing it here would bake this server's clock into an answer that goes stale the moment it is sent. The response carries no `index_age_seconds`, unlike the task and goal listings, because claims are read live from git-rest and no index describes them. ⚠️ **This route required the `/`-joined claim key first, and that is not incidental.** Deriving `scope` and `id` from a key is the inverse of the derivation, and under the old hyphen join `claims/repo/a-b-c` could not be split back into an owner and a repo at all — a listing would have returned claims that no caller could address. The ordering is the reason the key repair went first.

## v0.17.0

- fix: **Join the repository claim key with `/` instead of `-`, because the hyphen join silently made two repositories share one lock.** A claim is a mutual-exclusion primitive, and its key has to identify exactly one object. It did not: `repoClaimScope` built `claims/repo/<owner>-<repo>`, and a hyphen is legal inside both components — `validClaimComponent` accepts `[a-z0-9._-]` — so `owner=a-b, repo=c` and `owner=a, repo=b-c` both derived `claims/repo/a-b-c`. Two distinct repositories therefore aliased one lock, which means the exclusion did nothing and two runs could proceed against the same repository believing they held it. The join is now `/`, which cannot collide because `/` is rejected inside a component, and it matches the streak keys (`claims/redrive/<taskid>/<phase>/<n>`), which were already slash-separated. ⚠️ **This is a wire-format change and must be deployed in lockstep with `agent-task-executor`'s `DeriveClaimKey`, which derives the same key from the other side** — the format belongs to the executor, and a period where one side writes `claims/repo/a/b` and the other reads `claims/repo/a-b` is a period where the lock excludes nothing. In-flight claims carry a 5-minute lease, so a rolling deploy orphans each one for at most one lease, and the next acquire takes it over rather than refusing: `acquireToken` (`pkg/handler/claims.go`) reads the existing ref and, when `leaseExpired` holds, returns **that ref's own SHA** as the compare-and-swap token with no live holder, so the acquire succeeds instead of answering `409 claim_held`.

## v0.16.1

- fix: Persist the change-event baseline so a restart no longer skips the commits it missed. `--event-baseline-path` / `EVENT_BASELINE_PATH` names a file that outlives the process, and the feed resumes from the last published commit instead of adopting the current HEAD. Before this the baseline was process-local, so every commit pushed while the process was down was adopted silently and never published: a task's last record stayed at the phase it held when the instance was last up, and the executor drove it at that phase indefinitely. Two paths could drop the range — the restart gap, and a range abandoned after `MaxPublishRetries` — and this change repairs both. The abandoned-range path no longer persists the skip: the publish position moves past the abandoned range so later changes still publish, while the persisted baseline stays before it, so a restart re-attempts the range instead of dropping it for good. Empty keeps the previous process-local behaviour, so the flag is opt-in per instance.

- fix: Retain an abandoned publish range instead of persisting the skip, and classify sarama's client-side oversized-message error as permanent. An abandoned range used to advance the persisted baseline to head, so a range the feed deliberately skipped was dropped durably and a restart resumed past it. The feed now keeps two positions — the publish position, which moves past the range so later changes still publish, and the persisted baseline, which stays before it so a reload re-attempts the range. The abandon log line is replaced rather than supplemented: `abandoned_range_retained range=<from>..<to> baseline=<retained>` names the range and the baseline a restart resumes from, and the old `abandoning changes from … resuming at <head>` wording is gone. Separately, `publisher.IsPermanent` now also classifies a sarama `ConfigurationError`: the producer rejects a message over `Producer.MaxMessageBytes` locally, before the broker sees it, so the error is not a `KError` and was classified transient — one oversized task body reset the retry budget on every tick and blocked every later change forever, never reaching the cap that exists to abandon a poison message.

- fix: Drop a persisted event baseline that names a commit the repository no longer holds. A re-cloned volume, a force-push or a `gc` can leave the stored SHA unresolvable, and `git diff-tree` then fails in a way that is not a broker error — so the feed classified it as transient and retried it forever, and publishing stopped permanently rather than degrading. Startup now resolves the baseline against the repository and falls back to adopting HEAD when it is absent, which is the behaviour every instance had before the file existed. A repository that cannot be read at all takes the same fallback rather than failing startup — the read API stays up — but it is logged as its own cause, so a broken `git-dir` is distinguishable from a baseline that is genuinely gone. Both outcomes do reset the baseline to HEAD on the next publish.

## v0.14.0

- feat: Add typed claim endpoints addressed by task identifier or repository, so a claim is a concept in the API rather than a key-value ref store. `POST`, `DELETE` and `GET /api/v1/tasks/{id}/claim` plus `POST /api/v1/tasks/{id}/claim/renew` take a claim on a task; `POST /api/v1/repos/{owner}/{repo}/claim` and its `renew`/`GET`/`DELETE` siblings do the same for a repository. A repository has no task of its own, so its claim carries the claiming run's task identifier — the transport requires one on every ref write. The typed body is `holder` / `ttl_seconds` / `lease_token` and the transport underneath is git-rest's claim refs (`cluster` / `lease_until` / `expected_sha`), which a caller never sees; the lease defaults to 300 s and the response states `renew_before` 60 s ahead of expiry rather than leaving the caller to re-derive it. A lost compare-and-swap answers `409 claim_held` on acquire and `409 lease_lost` on renew or release — the two are different failures and are not collapsed. **An expired lease is free:** git-rest stores `lease_until` and never compares it, so a holder that died would otherwise block the key forever — every later acquire losing the compare-and-swap and answering 409 to a claim nobody holds. Acquire therefore reads the current ref and, when its lease has passed, retakes it carrying that ref's own SHA, so exactly one of several concurrent acquirers wins and the advertised lease is real rather than advisory. The 409 on a live claim now names the holder and its `lease_until`, `renew_before` is stated on the read route too, `ttl_seconds` is bounded at 24 h (above ~9.2e9 s the duration overflows and the lease would render already expired), and a 4xx from git-rest is answered 400 `invalid_claim` instead of 500 — a refused ref name is the caller's mistake, not a server fault. An unknown field in the body answers 400 `invalid_body` rather than being ignored, so a misspelled `ttl_seconds` cannot silently fall back to the default lease. New `pkg/gitrest.RefClient` carries the ref operations, since the existing client could only write whole files. **The repo key is the executor's, not a second spelling of it:** owner and repo are lowercased and joined with a hyphen exactly as the task executor derives them, because the executor is the other holder of these refs and two spellings of one repository would be two locks that do not exclude each other. A name outside `[a-z0-9._-]`, a leading `.`, a trailing `.lock` or a bare `..` answers `404` before any transport call, rather than reaching git-rest and coming back as a caller error.

## v0.12.0

- fix: Make `GET /readiness` describe the tree it is serving now, not the last build that succeeded. `Build` set `ready = true` and nothing ever cleared it, so a pod that had built once answered `200 ready:true` forever — measured on sun, whose vault-api reported `{"ready":true,"index_age_seconds":6696,"head":"e8aca81e"}` while its tree sat 111 minutes and 414 commits behind remote `35643048`, because the git-rest puller that used to advance it had been retired. `handleReadiness`'s 503 branch was unreachable dead code. A failed rebuild now clears the flag (the previous index keeps serving, so a read never fails on a transient read error) and the next successful one restores it. **`ready` also requires two freshness signals inside `--stale-after` (default `5m`, ten times the 30 s `--refresh-interval`), because a successful build says nothing about whether the tree still exists in a live state:** `index_age_seconds` is now the age of the last *confirmation* that the index matches the tree — advanced on every refresh tick that finds the HEAD unmoved, not only on a rebuild — and the new `tree_age_seconds` is the age of `.git/FETCH_HEAD`, the puller's heartbeat, since every `git fetch` rewrites it even when it brings nothing new. The two are separate because they fail independently: a rebuild can fail on a live tree, and a tree can freeze under a healthy loop. **The tree signal is the one that catches sun, and it cannot be replaced by an age threshold on the build alone:** a quiet vault whose tree still matches its remote is indistinguishable from a frozen one by any in-pod read of HEAD, and a naive `index_age_seconds > N` rule would have marked the live `vault-api-trading` on nuke dev not-ready at `index_age_seconds: 10357` while its tree matched remote `a4526b15` exactly. `--stale-after=0` disables the rule for a local run against a tree nothing fetches; `tree_age_seconds` is `null` when the tree carries no `FETCH_HEAD` to measure, and that half of the rule is then skipped rather than guessed. **Operational consequence:** `/readiness` is the `readinessProbe` on all three deployments, so a pod whose tree stops being fetched now leaves its Service endpoints after ~30 s instead of serving stale data indefinitely — the point of the change, and the trade it makes. `/healthz` is untouched, so a red readiness never restarts a pod.
